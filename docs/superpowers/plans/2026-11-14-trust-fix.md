# Trust Fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make governance of fintech-data-mesh a trust boundary: verified identity for people and workloads, one enforcement point in front of every product read path, stored and expiring grants, layered platform/domain policy, attested lineage, and runnable before/after demos.

**Architecture:** A new `platform/boundary/` FastAPI service is the only route to product data. It verifies a JWT (person) and a client certificate forwarded by an mTLS gateway (workload), asks OPA for a decision built from the platform guardrails and the domain policy, checks a Postgres grant where required, masks through the existing `mask_rows`, audits, and returns rows with a `lineage_verified` flag. Discovery authenticates the same way. Data stores sit on an internal Docker network with no published ports.

**Tech Stack:** Python 3.12, FastAPI 0.104.0, PyJWT, cryptography (Ed25519, X.509), httpx, psycopg 3 (grants), rdflib (SPARQL parsing), OPA 1.0.0 (Rego v1), Docker Compose, Fuseki 4.9.1.

**Spec:** `writing/scratch/fintech-trust-fix/trust-fix-brief.md`

## Global Constraints

- OPA is pinned to `1.0.0` in compose and CI. Never `latest`.
- Rego uses `import rego.v1`.
- Default access decision is `allow := false`; default masking is `full_hash`.
- Any OPA, grant-store, audit or verification failure means deny, never a default value.
- No request body sets identity. `user_id` and `user_role` are rejected with 400.
- Policy path is `data_mesh/access`. Masking strategy path is `data_mesh/access/masking_strategy`.
- Fuseki configs keep only `fuseki:query` and `fuseki:gsp-r`. No `update`, no `gsp-rw`.
- Only the boundary and discovery publish host ports.
- Dev keys, dev CA material and `.env` are never committed. `.env.example` is committed.

## Review Focus

1. Missing, expired, wrong-audience or wrong-signature token → 401, no rows.
2. Request body carries `user_role` or `user_id` → 400 (old clients fail loudly).
3. SPARQL `INSERT DATA`, `DELETE`, `LOAD`, `CLEAR`, `DROP`, `CREATE` → refused, parsed not regex-matched.
4. Grant expired, wrong subject, wrong product or wrong workload → read refused.
5. Tampered snapshot or wrong signing key → `lineage_verified` false and, where the policy needs it, read refused.
6. Audit write failure → no rows returned.
7. Domain policy attempts to allow unmasked PII or unauthenticated read → guardrail overrides it.

### Task 1: Person identity (JWT) and dev IdP
**Files:** Create `shared/identity/__init__.py`, `shared/identity/jwt_verify.py`, `tools/dev-idp/make_keys.py`, `tools/dev-idp/serve.py`, `tools/dev-idp/users.yaml`; Modify `platform/discovery/backend/models.py`, `platform/discovery/backend/main.py`; Test `tests/unit/test_identity.py`.
- `verify_token(token: str, jwks: dict, *, issuer: str, audience: str, now: datetime | None = None) -> Principal` where `Principal` is a dataclass `(subject: str, roles: frozenset[str], claims: dict)`. Uses PyJWT with `algorithms=["RS256"]`, checks `iss`, `aud`, `exp`, `nbf`. Any `jwt.PyJWTError` → raises `AuthError`.
- `fetch_jwks(url) -> dict` cached with a 5-minute TTL; failure → `AuthError`.
- FastAPI dependency `require_person(request) -> Principal`: missing or malformed `Authorization: Bearer` → 401.
- Dev IdP: `make_keys.py` writes `tools/dev-idp/keys/` (gitignored); `serve.py` serves `/.well-known/jwks.json` and `/token` for named users in `users.yaml` (analyst, risk_analyst, fraud_analyst, one owner per domain). Tokens: RS256, `iss=http://dev-idp`, `aud=data-mesh`, `sub`, `roles`.
- Discovery: `AccessRequest` loses `user_id` and `user_role`; a body containing either key → 400 via a `model_validator(mode="before")`. `request_access` takes `principal = Depends(require_person)` and uses `principal.subject` and the roles claim (the first role claim is the policy role).
- Verify: `pytest tests/unit/test_identity.py tests/unit/test_access_requests.py` (existing access-request tests are updated to send tokens).

### Task 2: Workload identity (mTLS, SPIFFE)

- `spiffe_id_from_pem(pem: str) -> str`: parses the certificate with `cryptography`, returns the single `spiffe://` URI SAN, raises `IdentityError` if absent or more than one.

### Task 3: Layered policy (guardrails + domain)

- Package `data_mesh.guardrails`: `deny_reasons` set; `allow_platform` true only if `input.principal.subject` present, `input.workload.spiffe_id` present, `input.action == "read"` or the request is an approval. `masking_floor(column_classification)`: `pii` → at least `partial_mask`; `never_writes` on the read path.
- Package `data_mesh.domain.<product>`: `allow` and `masks[column]` and `requires_approval`, read from the product file.
- Package `data_mesh.access` (decision): `allow := allow_platform and domain_allow`; `masking_strategy` is the stricter of platform floor and domain strategy (strictness order: `no_mask < partial_mask < hash_mask < full_hash < full_mask`).
- Rego tests prove a domain rule that allows unmasked PII is masked, and a domain rule allowing an unauthenticated read is denied.

### Task 4: Boundary service and read path
**Files:** Create `platform/boundary/__init__.py`, `platform/boundary/main.py`, `platform/boundary/policy.py`, `platform/boundary/reader.py`, `platform/boundary/fixtures/*.json`; Modify `platform/governance/enforce.py` only to accept a `write_audit` injected by the boundary (its signature is unchanged); Test `tests/unit/test_boundary_read.py`.
- `GET /products/{product_id}/rows?columns=a,b`: `Depends(require_person)`, `Depends(require_workload)`; reads rows via `ProductReader.read(product_id, columns) -> list[dict]` (fixture reader for the demo profile; pyiceberg adapter is a residual); asks OPA for the decision and masking; checks grant if `requires_approval`; calls `mask_rows`; audits; returns `{rows, lineage_verified}`.
- Every failure path returns 401/403/503 and no rows. Audit is written before rows are returned, and an audit failure returns 503.
- Audit record fields exactly as brief A7: subject, roles, workload SPIFFE ID, product, columns, decision, masking strategies, platform and domain policy revisions, grant id, `lineage_verified`, timestamp.
- Policy revisions: the boundary reads the OPA bundle revision from `GET /v1/policies` ids (or a content hash of the policy directory when that is unavailable). Document the choice.
- Verify: unit tests with a stubbed OPA transport and in-memory grant store: no token → 401; no cert → 401; OPA error → 503 no rows; audit error → 503 no rows; unclassified column masked.

### Task 5: SPARQL side door
**Files:** Create `platform/boundary/sparql.py`; Modify `platform/boundary/main.py`; Test `tests/unit/test_boundary_sparql.py`.
- `parse_read_only(query: str) -> None`: uses `rdflib.plugins.sparql.parser.parseQuery` and `parseUpdate` on the text; if `parseUpdate` succeeds, or the parsed query form is not `SelectQuery`, `AskQuery`, `ConstructQuery`, `DescribeQuery`, raise `ReadOnlyViolation`.
- `POST /products/{product_id}/sparql`: same auth chain as Task 4, forwards the query to `FUSEKI_<DOMAIN>_URL` (internal network) with `Accept: application/sparql-results+json`; masks bindings whose variable is a PII predicate (`customerName`, `customerEmail`, account identifiers) per the same policy function used for rows.
- Verify: parametrised test over `INSERT DATA`, `DELETE WHERE`, `LOAD`, `CLEAR`, `DROP`, `CREATE` → `ReadOnlyViolation`; a `SELECT` passes parsing.

### Task 6: Grants (Postgres) and approval
**Files:** Create `platform/boundary/grants.py` (`GrantStore` protocol, `PostgresGrantStore` with psycopg 3, `MemoryGrantStore` for tests), `platform/boundary/approvals.py`; Modify `platform/discovery/backend/main.py` (approval endpoint replaces in-memory approval); Test `tests/unit/test_grants.py`.
- Grant record: `{id, subject, workload_spiffe_id, product_id, columns, purpose, expires_at}`.
- `POST /api/access-requests/{id}/approve` requires a person whose subject is the product's `owner` (from the token's `owner` claim or a `groups` claim matching the product owner). Creates the grant in Postgres. Expiry = now + `time_limit_days` or `approval_sla_hours`, whichever the policy's `grant_ttl_hours` gives (default 24).
- `GrantStore.find_valid(subject, workload, product_id, columns, now) -> Grant | None`: returns only unexpired matches.
- Honor `approval_required` and `approval_sla_hours` from the product (the `approval_required` value is copied into the policy input).
- Verify: unit tests with MemoryGrantStore: expired grant denies; wrong subject denies; grant is used and its id appears in audit. An integration test runs against the compose Postgres when `POSTGRES_DSN` is set.

### Task 8: Lineage attestation
